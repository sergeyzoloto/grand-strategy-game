### Wrinkle worth a decision before Stage 1.3 proceeds

`HLT-032` (Public Health Statistics and Vital Registration, 1662) **enables**
`HLT-033` directionally — a real `prereqs`/`enables` pair, not a loose
`see_also`. `HLT-033`'s own (now-confirmed) `prereqs: [HLT-032]` is the
reciprocal half of that same link. The synthesis's Finding 2 treats HLT-033
as pure content to fold and retire; it doesn't address what happens to a
*directional dependency* HLT-033 was itself the target of.

Two options, not resolved by anything already written:

- **(a)** FIN-022 inherits `HLT-032` as a `prereqs` entry, on the theory
  that the mortality-table material FIN-022 is absorbing genuinely did
  depend on systematic vital registration existing first (Halley's 1693
  table used Breslau parish records — registration is a real precondition
  for *that specific input*, even though FIN-022's fire-insurance content
  has no such dependency).
- **(b)** The directional link is dropped entirely. HLT-032 instead gets a
  plain `see_also: [FIN-022]` (non-directional, "related," not "required
  by") on the theory that FIN-022 as a *merged* entry is no longer
  specifically the actuarial-table entry HLT-032 was built to feed, and
  forcing the whole entry (fire insurance included) to prereq a vital-
  registration entry overstates the dependency.

I'd default to **(b)** if forced to choose — a merged entry inheriting a
directional prereq that only actually explains a third of its content
(the folded-in third) reads like exactly the kind of imprecise link this
whole repair pass exists to prevent, not fix. But this is a genuine
judgment call the synthesis document never made, so flagging rather than
deciding. **Waiting for your call before Stage 1.3 proceeds on this
point specifically** — everything else in 1.3 is unaffected either way.

## 4. RETIRED-ID QUESTION

`conventions.md` says IDs are frozen and never reassigned, and separately
that "if an entry is cut, its number stays retired" — but nothing records
*why*, *when*, or *to what* a retired ID's content moved. This project has
already retired two IDs this session (`MIG-020`, merged into `MIG-018`
before this document existed; `PHI-006`, converted to the `axial-age`
thread page) with no durable record of either beyond a commit message and
a sentence inside the surviving entry. That's already thin; two more
retirements this pass make it thinner.

Proposed minimal mechanism — `_meta/retired-ids.md`, a flat table, append-
only, no prose:

```markdown
# Retired IDs

Append-only. An ID is never reassigned or reused once it appears here —
see `conventions.md`. This table is the durable record of what a retired
ID *was* and *where its content went*, since neither survives in the
domain folder itself once the file is deleted.

| ID | Title | Retired | Superseded by | Reason |
|---|---|---|---|---|
| MIG-020 | (recover title from commit history) | (date) | MIG-018 | Merge |
| PHI-006 | The Axial Age | (date) | `_meta/threads/axial-age.md` | Converted to thread page |
```

Columns: `ID`, `Title` (so the table is legible without cross-referencing
git history), `Retired` (date), `Superseded by` (an ID, a thread-page path,
or "—" if content was cut outright with nothing replacing it), `Reason`
(one of: Merge / Split / Cut / Thread-page conversion). I'd backfill the
two pre-existing retirements from git log/commit messages if you want the
table to open complete rather than starting mid-history — flagging that as
a small extra scope decision, not assuming it.
